1 Introduction & Architectural Evolution

The way we build AI-powered systems has changed dramatically over the past three years. Early production deployments treated the LLM as a black box: you sent it a prompt and used the response. That was fine for demos, but it collapsed under the weight of real-world complexity — multi-domain queries, inconsistent tool selection, runaway costs, and no meaningful error recovery.

The industry has now converged on a third-generation architecture: Multi-Agent Collaboration. Rather than a single model doing everything, you compose a network of focused, specialised agents, each with a narrow scope. A traffic-directing supervisor routes work to the right specialist. Results are synthesised, quality-checked, and delivered through a hardened pipeline. This guide explains every component of that architecture, with a flow diagram for each pattern.

Evolution of AI System Architecture — Gen 1 → Gen 2 → Gen 3 Multi-Agent Collaboration
🌱

Gen 1 — Single LLM Invoke

One model, one prompt, one synchronous response. Zero observability. No retry. Fine for internal tools, breaks in customer-facing production under load.

📊

Gen 2 — Monitored LLM

Wrapped the LLM call with token counting, cost logging, timeout enforcement, and a basic retry loop. Still a single model but now survivable in production for simple workloads.

🤝

Gen 3 — Multi-Agent Collaboration

Supervisor routing, specialist agents with focused tool sets, structured state handoffs, quality reflection, graceful degradation, semantic caching, and full distributed tracing.

Core Design Principle

The right architectural pattern depends on four axes simultaneously: task complexity, reliability SLAs, latency budget, and cost ceiling. All four must be considered together — optimising for only one will break the others.

Why Specialisation Wins

An LLM's reasoning quality degrades as its context window fills with irrelevant information. When a billing agent is also carrying tool definitions for order management, technical diagnostics, and subscription management, the model wastes attention on irrelevant paths. A specialist agent loaded with only its own 3–5 tools makes sharper decisions, has a shorter prompt, runs faster, and costs less per call. The supervisor exists precisely so that no individual agent ever needs to be a generalist.

This mirrors how humans organise large organisations: a manager (supervisor) understands the big picture and knows which department to call, but does not personally execute every task. The accountant (billing agent), the engineer (tech agent), and the logistics team (orders agent) each have deep expertise in a narrow domain.

2 Pattern 1: Supervisor Agent

The Supervisor pattern is the most broadly applicable starting architecture for production AI systems. At its core, a lightweight Supervisor Agent acts as a traffic director: it reads the incoming request, classifies the intent, routes to the most capable specialist, receives a structured result, and synthesises a user-facing response. The supervisor itself never executes business logic — that belongs to specialists.

The Anti-Pattern First: Why One Giant Agent Fails

Before the Supervisor pattern became standard, the most common approach was to create a single, large agent loaded with every possible tool. Need to handle orders and billing and technical support? Just give the agent all the tools. This seems simpler in development, but it fails catastrophically in production for three reasons:

  • Context Pollution: The LLM's context window fills with definitions for tools it will never use on a given request. This degrades reasoning quality and increases latency.
  • Wrong Tool Selection: With 20+ tools available, the model occasionally selects the wrong one — calling a refund tool when the user asked about order status. These errors are hard to detect and expensive to debug.
  • Unbounded Growth: As the system grows, new tools keep being added to the one agent. Over time it becomes an unmaintainable monolith that no individual understands completely.
Anti-Pattern: One Giant Agent — every request floods context with irrelevant tool definitions, causing wrong tool selection and brittle behaviour
Anti-Pattern

One Giant Agent

  • All tools loaded for every request
  • Context pollution → wrong tool calls
  • Grows without bound over time
  • Single point of failure across all domains
  • Expensive: every call uses full context length
Best Practice

Supervisor + Specialists

  • Supervisor carries only routing logic
  • Each specialist carries only its own tools
  • Each specialist independently deployable
  • Failure in one domain does not cascade
  • Cheaper: specialists use small, focused contexts

The Optimal Solution: Delegated Hierarchy

In the Supervisor pattern, the user request first hits the supervisor, which performs a lightweight classification pass — typically a small, fast model call that costs a fraction of a cent — to determine the request domain. It then routes to the appropriate specialist. The specialist executes the task with its own focused tool set, returns a structured result, and the supervisor synthesises the final response. Crucially, the supervisor does not need to understand how billing works or how orders are looked up — it only needs to know which agent to call.

Supervisor Pattern — Delegated Hierarchy: User request → Supervisor (classify + route) → Specialist Agents → Synthesis Node → Final Response

Shared State — The Communication Protocol

How does information flow between the supervisor and specialists? Through a shared state object — an immutable record that accumulates fields as it moves through each stage of the workflow. The initial state contains only the raw user request. After the supervisor runs, it adds a route field. After the specialist runs, it adds specialist_result and agent_used. After synthesis, it adds final_response. This object is the audit trail: you can replay any conversation and inspect exactly what each agent saw and produced.

Shared State Pipeline — the state object accumulates immutable fields as it passes through each workflow node, creating a full audit trail

Strict Supervisor Responsibilities

✅ Supervisor SHOULD

  • Classify the domain of the incoming request
  • Select the single most appropriate specialist
  • Pass only relevant context to the specialist
  • Receive the structured result from the specialist
  • Synthesise the final user-facing response
  • Handle specialist timeouts gracefully with a fallback
  • Log the route taken for auditing and debugging

❌ Supervisor SHOULD NOT

  • Execute domain tools directly (orders, billing, etc.)
  • Contain business logic for multiple domains
  • Grow into a "smart router with side effects"
  • Hold domain-specific prompts or few-shot examples
  • Make parallel calls unless explicitly designed for it
  • Cache results from prior conversations without explicit logic

When to Scale the Supervisor

A single supervisor works well for up to ~8 specialist agents. Beyond that, consider a hierarchical supervisor model: a top-level supervisor routes to domain supervisors (e.g., "Commerce Supervisor" and "Support Supervisor"), each of which manages its own set of specialists. This keeps classification prompts short and routing decisions fast at every level. 

// Hierarchical supervisor routing (pseudo-code)
TopSupervisor.route(request) → "commerce" | "support" | "technical"

CommerceSupervisor.route(request) → "orders" | "billing" | "subscriptions"

OrdersAgent.execute(request, tools=[lookup_order, track_shipment])

3 Pattern 2: Agent-to-Agent (A2A)

The Agent-to-Agent (A2A) pattern discards the concept of a central orchestrator entirely. Instead, agents operate as autonomous peers in a mesh network. Each agent maintains a capability manifest — a structured declaration of what it can do, its performance characteristics, and its pricing. When an agent needs a capability it does not have, it broadcasts a need, receives bids from peers, evaluates bids against protocol-level rules, and contracts the winner to execute the task.

This pattern is inspired by real-world marketplace dynamics: you do not always go to the same vendor. You post a requirement, vendors quote, and you select based on price, reputation, and fit. A2A brings this flexibility to AI agent networks.

Capability Discovery Contract Negotiation Peer Execution Distributed Recovery SLA-Aware Routing Trust Scoring Emergent Collaboration
A2A Peer-to-Peer Mesh Network — Agent A broadcasts a need, agents B and C bid, Agent D is selected via SLA + budget criteria. Agent E has an irrelevant specialty and is ignored.

The A2A Negotiation Protocol — Step by Step

  1. Need Broadcast: An initiating agent (Agent A) recognises that it lacks a required capability — e.g., multi-modal vision analysis, real-time financial data retrieval, or code execution. It broadcasts a structured Request for Capability (RFC) to its peer registry, including: task description, required output schema, maximum acceptable latency, budget per call, data residency constraints, and a minimum confidence threshold.
  2. Capability Matching: Each peer agent evaluates the RFC against its own capability manifest. Agents that can fulfill the request respond with a Bid: their confidence score for this task type, estimated p50/p95 latency, cost per invocation, trust tier, and any hard constraints (e.g., "cannot process PII data outside EU region"). Non-matching agents remain silent.
  3. Negotiation & Selection: Agent A applies a scoring function to the received bids. Typical scoring weights: 40% accuracy confidence, 30% latency SLA fit, 20% cost, 10% trust tier. The highest-scoring peer is selected. If no peer scores above a minimum threshold, the initiating agent either escalates to a human or degrades gracefully.
  4. Execution & Exchange: The selected peer agent receives the task, executes it using its own tools and models, and may stream intermediate results back to the initiator (e.g., streaming partial analysis for long-running tasks). Intermediate artifacts — parsed documents, computed embeddings, partial summaries — can be shared to reduce redundant computation.
  5. Completion & Settlement: Agent A receives the final structured result, validates it against the expected output schema, logs the interaction (peer ID, latency, cost, quality score) for future bid scoring calibration, and continues the workflow. If the result fails validation, Agent A may renegotiate with the next-best bidder.
When to Use A2A
  • Large-scale platforms with many independent capability providers
  • Marketplace architectures where agent quality/cost trade-offs change dynamically
  • Systems where capability needs are unknown at design time
  • Multi-tenant AI infrastructure where agents are contributed by different teams
  • Workloads needing autonomous load-balancing across heterogeneous providers
When NOT to Use A2A
  • Systems requiring strict, deterministic audit trails (financial regulation, HIPAA)
  • Small teams where coordination overhead outweighs benefits
  • Latency-critical paths where negotiation round-trips are unacceptable
  • Systems lacking distributed tracing infrastructure (A2A failures are hard to debug)
  • Early-stage products where a supervisor pattern is sufficient

A2A vs. Supervisor — The Key Difference

In the Supervisor pattern, the routing logic is programmed — the supervisor knows in advance which specialists exist and what they do. In A2A, routing is discovered at runtime through negotiation. The Supervisor is deterministic and auditable; A2A is flexible and emergent. Neither is universally superior — use the right tool for the context.

5 Advanced Workflows & Pipelines

Production AI systems rarely use a single pattern in isolation. Advanced workflows combine routing, reflection, parallelism, and checkpointing into layered pipelines that handle the full request lifecycle — from raw input to quality-assured output — with built-in mechanisms for self-correction, partial failure recovery, and cost management.

The Reflection Loop — Self-Correcting Output Quality

The Reflection Loop is one of the highest-impact patterns for improving output quality without human review. The system runs the Generator Agent to produce an initial draft, then immediately runs a separate Critic Agent that evaluates the draft against a rubric. If the score is below a threshold, the draft — along with the critique — is fed back to the Generator as context for a revised attempt. The loop continues up to a configured retry limit, after which the system escalates to a human reviewer.

The Critic Agent is the key design element. It must score on specific, measurable dimensions — not "is this good?" but "does this response contain the requested information? (0–25 pts) Is it free from hallucination? (0–25 pts) Does it comply with policy? (0–25 pts) Is the tone appropriate for the audience? (0–25 pts)". This gives the Generator concrete, actionable feedback to improve on.

Agentic Reflection Loop — Generator produces a draft, Critic scores it. Score below 80 → Regenerate with critique as context (max 3 retries). Score 80+ → Approved Response. Max retries exceeded → Escalate to human review.

Designing a Good Critic Prompt

The Critic Agent's prompt should be concrete and rubric-based, not vague. A weak critic prompt: "Evaluate whether this response is good." A strong critic prompt:

You are a strict quality evaluator. Score the response across four dimensions:

1. ACCURACY (0-25): Does the response correctly answer the user's question?
   Penalise any factual claims not supported by the provided context.

2. POLICY COMPLIANCE (0-25): Does the response avoid prohibited topics?
   Check against policy list: [medical_advice, legal_advice, competitor_names]

3. COMPLETENESS (0-25): Does the response address all parts of the user's question?

4. TONE (0-25): Is the tone professional, empathetic, and appropriate?

Output ONLY valid JSON:
{"accuracy": int, "policy": int, "completeness": int, "tone": int,
 "total": int, "critique": "specific actionable feedback for improvement"}

Parallel Fan-Out / Fan-In — Reducing Latency with Concurrency

For tasks that can be decomposed into independent subtasks, running specialists sequentially wastes time. Parallel Fan-Out spawns multiple specialist agents simultaneously, each working on a different aspect of the problem. A Fan-In Merger then waits for all results, handles partial failures (e.g., one specialist timed out), and produces a merged output.

This is the LLM-native equivalent of parallel processing in distributed computing. A sequential pipeline of three 2-second agents takes 6 seconds. The same pipeline with fan-out takes 2 seconds — a 3× latency improvement with the same quality of output.

Fan-Out / Fan-In Pipeline — the Coordinator decomposes the task, Researcher, Analyst, and Critic agents run in parallel (reducing total latency by ~3×), and the Merger Node aggregates results and handles partial failures

Critical Rules for Pipeline Design

  • Idempotency: Every node must produce the same output given the same input. This enables safe retries after failures without side effects (e.g., duplicate database writes, double-charged payments).
  • Checkpointing: Persist the shared state after every node completion. If the pipeline fails at Node 4, you resume from Node 4's checkpoint — not from the start. This is non-negotiable for long-running pipelines.
  • Per-Node Timeout Budgets: Never let one slow specialist block the entire pipeline indefinitely. Assign each node a timeout (e.g., Researcher: 8s, Analyst: 12s, Critic: 4s). If a node times out, the Merger receives a partial result and handles it gracefully.
  • Dead Letter Queues (DLQ): Failed pipeline runs must land in a DLQ for human inspection and potential reprocessing. Silent failure — where tasks are dropped without a trace — is unacceptable in production.
  • Back-Pressure: When downstream nodes are overloaded, upstream nodes should slow their intake rather than queuing unlimited work in memory. Implement explicit queue depth limits with back-pressure signalling.

6 Routing & Cost Optimization

LLM inference cost is a first-class engineering concern, not a finance concern. At scale, the difference between routing every query to GPT-4o versus routing intelligently can mean the difference between a profitable product and an unsustainable one. A well-designed cost routing layer can reduce inference costs by 60–80% with no measurable quality degradation on the majority of queries — because most queries do not need a frontier model.

Complexity-Based Model Routing

The key insight is that query complexity follows a heavy-tailed distribution: the majority of queries are simple (FAQ, status lookups, rephrasing), a substantial minority are medium complexity (summarisation, Q&A over a document), and only a small fraction genuinely require frontier-model reasoning (multi-step planning, novel problem-solving, sensitive decisions). A lightweight Complexity Classifier — itself a small, fast, cheap model — reads the query and outputs a routing label. The cost of the classifier call is negligible compared to the savings from routing correctly.

Intelligent Cost Router — a lightweight Complexity Classifier (≈$0.001/call) dispatches to Haiku/Flash (SIMPLE), Sonnet/GPT-3.5 (MEDIUM), Opus/GPT-4o (COMPLEX), or Human+LLM (SENSITIVE). All results flow through a Unified Response & Cost Log.

Multi-Layer Caching Strategy

Caching is the single highest-leverage optimisation for LLM systems. The best LLM call is one that never happens. Layer your caching strategy from cheapest to most expensive:

Implementation Order

Layer your caching in this order: (1) Exact-match cache first — highest ROI, lowest risk. (2) Prefix caching — enable at the API level for free. (3) Complexity routing. (4) Semantic caching. (5) Batch inference for async workloads. Do not implement all layers at once — measure each layer's impact before adding the next.

7 Production Hardening Pipeline

Shipping an agent to production is not the endpoint — it is the beginning of a continuous hardening process. Production AI systems require multiple overlapping layers of defence: input validation before the LLM ever sees a query, intelligent routing to the right model and cache tier, safe agent execution with circuit breakers, output guardrails before the user receives a response, and always-on observability that captures cost, latency, quality, and policy compliance simultaneously.

The hardening pipeline is not a single component. It is a philosophy applied at every layer — and each layer must be independent enough to function even if adjacent layers experience failures.

Production Hardening Pipeline — Defence in Depth: 5 independent layers each providing a safety boundary. Failure at one layer does not compromise the others.

🛡️ Layer 1: Input Validation

Before any LLM call, every input must pass:

  • Schema validation: Required fields present, correct types, within length limits. Reject malformed requests with a 400 before they reach the model.
  • PII detection & masking: Identify and redact personal identifiers (emails, phone numbers, SSNs, names) before they enter the prompt. Use a lightweight NER model or regex patterns with human review for edge cases.
  • Prompt injection detection: Scan for attempts to override the system prompt (e.g., "Ignore previous instructions…"). Flagged inputs should be rejected or quarantined, not silently passed through.
  • Rate limiting: Enforce per-user, per-tenant, and per-endpoint rate limits. Prevent both accidental abuse (buggy clients) and intentional attacks.

🚦 Layer 2: Intelligent Routing

After validation, determine the cheapest path to a correct answer:

  • Cache lookup first: Check exact-match and semantic cache before any model call. Cache hits are free — never skip this step.
  • Complexity classification: Route to the right model tier (Haiku → Sonnet → Opus) based on query complexity. A misrouted query to Opus that Haiku could handle is pure waste.
  • Feature flags: Enable gradual rollouts of new models or routing rules. Send 5% of traffic to a new model, measure quality and cost, then increase the percentage. Never do a full cutover without data.

⚙️ Layer 3: Agent Execution

The core execution layer must be safe and bounded:

  • Tool call sandboxing: Agent-initiated tool calls (database queries, API calls, code execution) must run in a sandboxed environment with explicit allowlists. An agent should never be able to make an arbitrary outbound HTTP request to an unknown domain.
  • Circuit breaker: Each external dependency (LLM API, tool, database) is wrapped in a circuit breaker. When error rates spike, the circuit opens — rejecting calls immediately and returning fallback responses until the dependency recovers.
  • Timeout enforcer: Every agent call has a hard wall-clock timeout. A slow LLM API should not block a user for 120 seconds — fail fast, return a graceful error, and let the fallback hierarchy handle it.

🔍 Layer 4: Output Guardrails

Before any response reaches the user:

  • Reflection scoring: Run a fast Critic Agent over the response. If the score is below threshold, retry or escalate — never deliver a low-quality response to the user.
  • Policy filter: Check the response against the policy blocklist (competitor mentions, prohibited medical/legal advice, harmful content). Blocked responses are replaced with a safe fallback message.
  • PII re-masking: If PII was masked at input, ensure it is not hallucinated back into the output. Also check that no new PII from the model's training data appears in the response.
  • Format validation: Validate that the output matches the expected format (JSON schema, markdown, plain text). Malformed outputs should trigger a retry, not be passed to the client.

Circuit Breaker Deep Dive

The Circuit Breaker is the most critical resilience pattern in production AI systems. It prevents cascading failures: when the LLM API is slow or returning errors, a system without a circuit breaker will continue hammering it with requests, causing the slow API to become even slower, causing timeouts to pile up, causing the entire system to become unresponsive. The circuit breaker breaks this feedback loop.

Circuit Breaker State Machine — CLOSED (normal operation) → OPEN (all calls rejected, fallback returned) when error rate exceeds threshold → HALF-OPEN (1 probe call) after timeout expires → CLOSED again on probe success, or OPEN again on probe failure

Circuit Breaker Configuration Reference

  • Error threshold: Typically 50% error rate over a 10-second window before opening. Adjust based on your SLA — stricter SLAs need a lower threshold (e.g., 20%).
  • Minimum request volume: Do not open on 1 error out of 1 request. Require at least 10–20 requests in the observation window before evaluating the error rate.
  • Open duration (cooldown): Start with 30 seconds. The circuit stays open for this duration before transitioning to HALF-OPEN for a probe.
  • Probe timeout: The single probe call in HALF-OPEN state gets a generous timeout (2× normal) to account for a slow-recovering service.
  • Fallback response: Never return a 500 error to the user when the circuit is open. Return a pre-generated graceful message: "I'm having trouble right now. Please try again in a moment." Log the circuit-open event to your alerting system.

Graceful Degradation — The Fallback Hierarchy

When a specialist agent is unavailable — due to circuit opening, timeout, or deployment issue — the system should never fail hard to the user. Design a four-level fallback hierarchy:

  1. Primary Path: Call the designated specialist agent with full context and wait up to the configured timeout. Succeeds in ≥ 99% of cases under normal operation.
  2. Secondary Path: On primary failure, retry with a simpler prompt against a smaller, more reliable model (e.g., drop from GPT-4o to GPT-3.5). Accept slightly lower quality for the sake of availability. Covers the majority of transient failures.
  3. Tertiary Path: Return a pre-generated, category-level cached response for this request type. Not personalised, but accurate and safe. Appropriate for FAQ-style queries that have stable answers.
  4. Quaternary Path: Deliver a graceful, empathetic "I'm unable to help right now" message with a suggested path to human support. Log the full request to a DLQ for human review. Never return an error stack trace, model output artefact, or "I don't know" without a clear next action for the user.

4 Pattern 3: Agent as a Tool — Production A2A Orchestration & Skills-Based Execution

Agent as a Tool

This section is regarding Agent as Tools and Skills-Based Execution of the Advanced Agentic AI Bootcamp. It extends the previous patterns with production-grade concepts: mixed-intent routing, agents-as-tools, skill registries, the Planner → Validator → Executor pipeline, and runtime governance.

The previous session established supervisor-to-specialist routing for clean, single-domain requests. Below section confronts the harder reality: real enterprise requests are rarely single-domain. A user saying "My order hasn't arrived and I was charged twice" needs the orders capability and the billing capability and potentially the policy capability — simultaneously. No single-route supervisor can handle this correctly.

The Mixed Intent Problem

Simple supervisor routing forces a binary choice: pick one specialist and route. But real customer problems do not arrive pre-sorted into clean categories. Consider two real-world examples:

"My order has not arrived, and I was charged twice. Please check both."

Requires: Orders + Billing + possibly Policy — all three simultaneously.

"The app crashed during payment, but money got debited."

Requires: Technical (crash) + Billing (debit) + Policy (refund decision).

Mixed Intent Problem — when a simple supervisor must choose exactly one route: Orders → misses billing, Billing → misses the order, General → too generic. All three are wrong.

The shift in thinking required here is fundamental: previously, one request mapped to one specialist. Now, one request must map to multiple controlled capabilities, executed in a coordinated way, with their results synthesised into a single coherent answer. This is what production A2A orchestration solves.

Agents as Tools — Specialists as Callable Units

Below section is the distinction between low-level tools and agent-level tools. A low-level tool is an atomic function: get_order_status, lookup_transaction, submit_return. These are fine for simple pipelines. But a whole specialist agent can also be exposed as a tool — orders_agent_tool, billing_agent_tool, policy_agent_tool.

When exposed this way, each agent-tool is not a single function. Internally it has its own system prompt, tool set, reasoning chain, validation logic, and structured output schema. The orchestrator sees it as a simple callable — but internally it is a full specialist agent with all its complexity encapsulated. This is the Agent-as-a-Tool pattern applied at the multi-capability level.

Agents as Tools — the Orchestrator Agent calls orders_agent_tool, billing_agent_tool, technical_agent_tool, policy_agent_tool, and rag_agent_tool as callable units. Each returns structured output. Synthesis combines them into the Final Answer.
The New Failure Mode

If the orchestrator can call any agent-tool any number of times without constraint, it will. An unconstrained orchestrator may call 5 agents when 2 would suffice, loop repeatedly, inflate costs, and balloon latency. Agent-as-tool is powerful, but it needs governance. The orchestrator can reason — the platform must enforce limits.

Tool Bloat & The Skills Solution

A tempting shortcut is to simply give the orchestrator every low-level tool directly. Why add the agent-as-tool abstraction? Because exposing 40+ tools to a single agent creates tool bloat — a critical anti-pattern that degrades the entire system.

Every tool has a name, a description, an input schema, and argument descriptions — all of which consume tokens in the context window. With 40 tools loaded, the model spends significant reasoning capacity just figuring out which tool is even relevant to the current request. This leads to higher token usage, higher cost, slower inference, and critically — wrong tool selection.

Tool Bloat — a Supervisor Agent loaded with 40 tool definitions suffers Context Window Pollution → Higher Input Tokens → Tool Selection Confusion → Wrong Tool Calls → Higher Cost + Latency. Tool bloat is context pollution.

What Is a Skill? Tool vs. Skill vs. Agent

The solution is to introduce a new abstraction layer — the Skill. Understanding the three levels is essential:

ConceptLayerExampleWhat it Does
Tool Atomic Action lookup_transaction One specific, deterministic function call. No reasoning.
Skill Packaged Capability billing_skill Groups related tools behind a contract. Has limits, fallbacks, structured output.
Agent Reasoning Unit supervisor_agent Decides what capability or action is needed. Reasons over skills, not tools.

A skill solves one capability area by grouping all the internal tools needed for that area. orders_skill internally uses get_order_status, get_tracking_url, and submit_return. billing_skill uses lookup_transaction, check_invoice, and request_refund. The supervisor never needs to see the internal tools — only the skill. This is information hiding applied to AI agent design.

Skills Reduce Tool Bloat — the Planner/Supervisor sees 5 skills (orders_skill, billing_skill, technical_skill, rag_skill, policy_skill) instead of 40 individual tool definitions. Each skill encapsulates its internal tools.

RAG Skill & Policy Skill — The Hidden Complexity

rag_skill

Internally coordinates three sequential stages: retriever (semantic search over a vector store), reranker (cross-encoder re-scoring of retrieved chunks), and context builder (selecting and formatting the final context window). The planner calls rag_skill and gets back a structured answer — it never knows about the internal 3-stage pipeline.

policy_skill

Internally checks against a rules engine, runs compliance checks, and evaluates whether the request requires escalation to a human. For billing issues above a threshold, policy_skill must always be included in the plan. This is a governance rule enforced at the validator level — not a prompt instruction.

Claude Skills — Parallel Concept

Claude Skills package instructions, scripts, and resources so the model loads only the right capability when needed — the same principle of reducing context bloat. The enterprise skill pattern from below production controls on top: each skill has a contract, allowed tools, runtime limits, fallback behaviour, structured output schema, and full observability. Mental model: Claude Skills solve context loading. Enterprise skills solve context loading + production governance.

Planner → Validator → Executor — Production Safety Pattern

Giving the supervisor direct access to skill tools works — but for enterprise systems, Below introduces a more controlled pattern: Planner → Validator → Executor → Synthesis. The key insight is the separation of planning from execution. The LLM plans; the platform validates; the platform executes. The LLM cannot bypass the validation step.

🗺️ Skill Planner

The LLM reads the user request and produces a structured Skill Plan — a JSON object specifying which skills to invoke, what each skill should do, why it was selected, and the priority. Critically, the planner does not execute anything. It only proposes. This allows the plan to be inspected, validated, and potentially rejected before any tool is called.

✅ Plan Validator

A deterministic component (not an LLM) that checks the plan against a ruleset: skill count ≤ max_skill_calls, every skill exists in the registry, user has permission to call the skill, high-risk billing tasks include policy_skill, estimated budget is available, no duplicate skill calls. The validator either passes the plan to the executor or rejects it with a reason for clarification/escalation.

⚙️ Skill Executor

Runs only the skills that passed validation, in the approved order. Each skill call goes through the Runtime Constraint Enforcement chain: skill allowed? → call limit? → budget? → timeout? Each produces a structured SkillOutput object. The executor collects all outputs and passes them to synthesis.

🔀 Synthesis

Merges all SkillOutput objects into a single coherent final answer. The synthesis layer also handles partial failures gracefully — if billing_skill succeeded but orders_skill timed out, synthesis answers the billing question and acknowledges the orders issue is being investigated, rather than failing the entire response.

Planner → Validator → Executor — User Request → Guardrail → Skill Planner (proposes) → Structured Skill Plan → Plan Validator (deterministic checks) → Invalid: Clarify/Reject/Escalate | Valid: Skill Executor → runs approved skills in parallel

Structured Skill Plan — What the Planner Produces

The planner does not produce a paragraph — it produces a validated JSON structure that the validator can inspect deterministically:

{
  "tasks": [
    {
      "skill_name": "orders_skill",
      "task": "Check why the order has not arrived.",
      "reason": "User mentioned delayed delivery.",
      "priority": "normal"
    },
    {
      "skill_name": "billing_skill",
      "task": "Investigate duplicate charge.",
      "reason": "User mentioned being charged twice.",
      "priority": "high"
    },
    {
      "skill_name": "policy_skill",
      "task": "Check whether refund or escalation policy applies.",
      "reason": "Billing issue may involve refund decision.",
      "priority": "high"
    }
  ],
  "requires_human": false,
  "reason": "Request contains order delay and duplicate billing issue."
}

This structured format means the validator can apply deterministic rules — not LLM judgment — to approve or reject the plan. Every check is a simple conditional, not another model call.

Plan Validation Rules (All Deterministic)

  1. Skill count ≤ max_skill_calls: If the plan requests 5 skills but the limit is 3, reject immediately. The LLM cannot reason its way around this — it is a hard numeric check.
  2. Every skill exists in the registry: If the plan references refund_skill and that skill doesn't exist in the registry, reject. This prevents hallucinated capability names.
  3. Tenant/user permissions: If the current user's tier is not allowed to invoke policy_skill, reject that task from the plan. The remaining tasks may still proceed.
  4. High-risk billing rule: Any plan containing billing_skill with a task involving refunds must also include policy_skill. This is a compliance rule enforced in code, not in a prompt.
  5. Budget check: Estimated cost of running all skills (sum of per-skill cost estimates) must not exceed the per-request budget cap. Reject if over-budget.
  6. Duplicate skill removal: If the planner included billing_skill twice (a common LLM hallucination), deduplicate. One call is sufficient.
  7. Unsupported requests: If no skill in the registry can address the request, return a clarification request to the user rather than attempting to handle it with an ill-suited skill.

Runtime Constraints & Governance

This is where most agent systems fail. Developers put constraints inside prompts: 

# WRONG — these are wishes, not enforcement:
"Use at most 3 tools."
"Do not call unnecessary agents."
"Keep cost low. Avoid loops."

Prompt instructions are suggestions to the LLM. They are not enforcement. The model may follow them most of the time — but under novel inputs, adversarial prompts, or simply unusual phrasings, it will break them. Real enforcement must happen in runtime wrappers, validators, and execution controls that live outside the prompt.

Runtime Constraint Enforcement — before any skill executes, four gates must pass: Skill Allowed? → Call Limit? → Budget? → Timeout? Only then does the skill run. Each NO path triggers a specific fallback. This is enforcement, not suggestion.
RUNTIME_LIMITS = {
    "max_skill_calls": 3,           # Maximum skills per request
    "max_tool_calls_per_skill": 2,  # Maximum internal tool calls per skill
    "max_total_cost_usd": 0.05,     # Maximum cost per request
    "max_latency_seconds": 20,      # Maximum wall-clock time
    "allowed_skills": [             # Allowlist — only these may be invoked
        "orders_skill",
        "billing_skill",
        "technical_skill",
        "rag_skill",
        "policy_skill",
    ],
}
The Core Principle

The LLM can choose the work. The platform must control the work. Prompts are suggestions; runtime wrappers are enforcement. Any constraint that must hold in production must be implemented in code — not in natural language instructions to the model.

Skill Contracts & Structured Output Schema

What makes a skill a production capability rather than a prompt folder is its contract. Every skill has a formally defined contract — not a vague description, but a structured specification of what the skill is responsible for, what tools it may use, what it must never do, and how it behaves when things go wrong.

Skill Contract (left) defines responsibility, allowed tools, forbidden actions, limits, and fallback. SkillOutput Schema (right) is the structured response every skill must return — enabling synthesis, logging, testing, and escalation automation.

Every skill returns a structured SkillOutput — not a paragraph of text. This structured output is what makes the entire system observable, testable, and synthesisable:

  • status: Tells the synthesis layer exactly what happened — resolved, needs more info, failed, or escalated. This drives synthesis behaviour without additional LLM reasoning.
  • confidence: A float between 0 and 1. Low-confidence outputs (e.g., below 0.7) can trigger automatic escalation to a human reviewer or a second-pass reflection check.
  • requires_human: A boolean flag that, when true, bypasses the synthesis layer entirely and routes directly to a human agent queue.
  • risk_level: Used by the synthesis layer to apply appropriate caveats. A high-risk billing answer is presented differently from a low-risk FAQ answer.
  • cost_usd and latency_ms: Actual measured values, logged per skill call. This enables per-skill cost attribution, SLA monitoring, and identifying which skills are most expensive.
class SkillOutput(BaseModel):
    skill_name: str
    status: Literal["resolved", "needs_more_info", "failed", "escalated"]
    answer: str
    confidence: float           # 0.0 – 1.0
    tools_used: list[str]
    requires_human: bool
    risk_level: Literal["low", "medium", "high"]
    cost_usd: float
    latency_ms: float

Full Production A2A Architecture

Final implementation combines all the patterns into a single, production-controlled pipeline. Below is the architecture of the final system, with guardrails at every stage — from input validation to plan approval to runtime constraints — and a clear separation of concerns between planner, validator, and executor.:

Full Production A2A Architecture : input_guardrail → skill_planner → plan_validator → [invalid: clarify_or_escalate] [valid: skill_executor → orders_skill, billing_skill, rag_skill, policy_skill] → synthesis → END. Trace logs capture per-skill observability throughout.

Key Takeaways

Routing Limit

Fixed supervisor routing works for clean single-domain requests. Real enterprise requests are mixed-intent and need multiple capabilities simultaneously.

Tool Bloat

Too many low-level tools create context pollution and degrade routing quality. Group them into skills with contracts.

Plan-Then-Execute

Planner-validator-executor is safer than free-form tool calling. The model proposes; the platform disposes.

Agents as Tools

Subagents exposed as tools let the orchestrator invoke multiple specialists per request. Without constraints, this creates new failure modes.

Skills

Skills group tools into production capabilities with contracts, limits, and structured outputs. Tools are implementation details. Skills are production capabilities.

Runtime Wrappers

Prompt constraints are not enforcement. Runtime wrappers enforce limits. Any constraint that must hold must live in code.

Final Principle

Agents should not be given every tool. Agents should be given the right capabilities, at the right time, under the right constraints. Production A2A does not mean agents randomly chatting — it means controlled collaboration, bounded by runtime governance, producing structured outputs, with full observability.

9 Conclusion

Multi-agent AI systems have crossed from experimental to essential. The three patterns in this guide — Supervisor, A2A, and Agent-as-a-Tool — represent the current state of the art for building AI systems that are reliable, cost-efficient, and maintainable at production scale. None is universally superior; each is a tool suited to specific constraints.

🧠

Supervisor Pattern

Your default starting point for customer-facing systems. Adds structure and domain separation without over-engineering. The right first pattern for 80% of teams.

🔗

A2A Pattern

For large-scale platforms where capability needs are dynamic and agent providers are contributed by multiple teams. Requires mature distributed systems infrastructure.

🔧

Agent as Tool

The most testable and maintainable pattern. Use it for any LLM capability that needs a stable contract, caching, versioning, or independent deployment.

The Four Non-Negotiables of Production AI

Regardless of which pattern you choose, these four properties must be built in from day one — retrofitting them is exponentially more expensive:

  1. Observability: Distributed tracing across every agent call, structured logging with correlation IDs, cost tracking per request, and quality dashboards. If you cannot measure it, you cannot improve it. Instrument before you ship.
  2. Idempotency: Every node, every agent, every tool call must be safely retryable. Design your side effects (database writes, API calls) to be idempotent from the start. Retrofitting idempotency into a live system is extremely painful.
  3. Graceful Degradation: Define your fallback hierarchy before your first production incident, not during it. Decide in advance: what does the system do when the LLM API returns a 503? When the database times out? When the circuit breaker opens? Document these paths explicitly.
  4. Cost Governance: Set per-request cost budgets and enforce them in code. Alert when average cost per session exceeds your target. Review the top 10% most expensive requests weekly — they are usually the ones with runaway tool loops or unexpectedly long contexts.
Final Thought

The AI engineering field is moving fast, but the underlying engineering principles are stable: separation of concerns, defensive programming, observability, and graceful degradation have been foundations of reliable software for decades. The patterns in this guide apply those principles to the specific constraints of LLM-based systems. Master the principles, and the patterns will evolve naturally as the technology does.
